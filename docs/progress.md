## Incident record IR-1 (2026-10-14): question 106 retired in the dev database by a test

| Item | Fact |
|---|---|
| What happened | The first run of `admin_integration_test.php` (run `18402869c6`) sent `POST /admin/questions/106/retire` as test administrator user 143 (`m5.18402869c6.admin@example.invalid`), expecting a refusal. Topic 1 had 12 valid quiz questions, so the API correctly retired the question. |
| Recorded by the system | `audit_log` row **#1**: admin 143, action `retire`, entity `question` 106, before `{"status":"active","revision":1}`, after `{"status":"retired","revision":1}`, at `2026-10-14 16:40:37.415` UTC. This is the only audit row in `hunter_system_dev`. |
| Effect while retired | Topic 1's pool went from 12 to 11 valid questions (still ready, threshold 10). New quiz starts on topic 1 could not pick question 106. The 22 existing attempts that include question 106 were unaffected: their snapshots and grades are immutable and were not touched. No other test ran in that window. |
| Correction | Performed by the developer's database-admin connection (`root`), **outside the API**: `UPDATE questions SET status = 'active', retired_at = NULL WHERE id = 106 AND status = 'retired' AND revision = 1` (1 row). Verified: status `active`, revision 1, `retired_at` NULL, topic 1 pool 12. Its `updated_at` still shows the retire time (`16:40:37.372`); it was deliberately not rewritten. |
| Why no audit row for the correction | `audit_log` requires an administrator user (`fk_audit_log_admin`), and the v1 API has no action that reactivates a retired question (retired is final, D-53). Writing a row would attribute a root-console change to an administrator who did not make it, so **no audit row was inserted**; this record is the documentation of the correction. Audit row #1 is preserved unchanged (append-only). |
| Root cause and fix | Test-design error: the check assumed topic 1 sat at the readiness threshold. The dev suite now performs only refusals that cannot write (here: a stale `expected_revision`), and it fingerprints dev content and the audit-row count before and after (V3). All successful mutations, including the below-threshold and assessment-quota refusals that need content at a threshold, run only on the fixture database. |
| Follow-up | Any future administrator "reactivate" capability, or an admin-visible incident note, would need a product decision; none was added. |
